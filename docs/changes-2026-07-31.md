## 1. The `retell` action queue finally has a poller

`advance_referral()` has always queued `contact_service_by_phone` to component `retell`
once a referral clears consent + has a chosen service whose next unused channel is
`phone`. Nothing ever claimed it — `backend/call_agent/db.py`'s own comments and
`docs/whats-left.md` A4 said so explicitly: *"nothing polls that action type... we
dispatch calls via direct HTTP instead."* That direct-HTTP dispatch
(`POST {CALL_AGENT_BASE_URL}/place-referral-call`) already existed; it just had no
caller.

**New: [`backend/orchestrator/voice_component.py`](../backend/orchestrator/voice_component.py)**
— third component alongside `karthik_form`/`backend`, added to `worker.py`'s
`COMPONENTS` tuple so it drains every tick. A4 assigned this to Voice; confirmed ours to
build (2026-07-31) since we own both ends of this integration for testing.

- **Call placed successfully** → the action is marked `blocked`, not `completed`, and
  this module does **not** call `advance_referral()` itself. `call_agent`'s own
  `/log-call-outcome` webhook is what writes the `attempts` row, closes the action, and
  re-advances the referral once the call actually concludes
  (`_close_action_and_advance`). Marking it `completed` here would let
  `advance_referral` re-queue the same channel under an already-dead dedup key (§7c).
- **`escalated: true`** (call_agent's own 3-attempt cap already hit) → no call was
  placed and no webhook is ever coming, so this path closes the action itself
  (`completed`) and calls `advance_referral()` directly — the one case where nobody
  else will.
- **Any exception** (unreachable, non-2xx, tunnel down) → marks the action `failed`,
  matching `actions.py`/`backend_component.py`'s existing convention exactly. Chosen
  deliberately over bespoke retry logic, at the cost of the same poisoned-dedup-key
  risk as the Emily-consent bug (§7c) — a referral that hits this needs a manual DB fix
  to retry.
- `backend/main.py`'s dashboard integration panel now shows `retell` as
  `"polled_by_us": True`.

## 2. `save_call_outcome` no longer silently drops the booking confirmation

Found by comparing live DB state before/after a real confirmed call: the `attempts` row
was written correctly (`outcome='scheduled'`), but `service_bookings.booking_status`
stayed `'pending'` forever — `confirmation_number`, `booked_at`, etc. all silently never
applied.

Root cause: Retell sends `pickup_window: ""` — an empty string, not `null` and not
omitted — when it has nothing to report. The old `payload.get("pickup_window") is not
None` guard let that through, and `scheduled_start_at` is a `timestamptz` column:
writing `""` into it is a type error that fails the **entire** `.update()` call (one bad
field kills every field in the same statement). Because that exception was unhandled,
it also aborted everything `main.py`'s `log_outcome` does *after* `save_call_outcome`
returns — closing the action, calling `advance_referral()`, and forwarding to our
`/api/voice/call-outcome` (the only thing that queues the patient's `notify_patient`
WhatsApp). One bad field silently broke the entire rest of the post-call chain.

**Fixed:** `pickup_window`/`offered_datetime` are now checked for truthiness, not just
non-`None` — `""` is treated the same as missing. The `service_bookings` update is also
now wrapped in its own try/except, so if *anything else* unexpected fails there in the
future, it can't also block closing the action, advancing the referral, or notifying
the patient — the failure is recorded in the response instead of raised.

> ⚠ **This fixes the code in this checkout only.** `call_agent` is deployed separately
> on Railway; this fix does nothing for real calls until that service is redeployed
> from the updated code.

## 3. `get_or_create_booking_id` materializes the booking row Voice needs

Nothing upstream ever created a `service_bookings` row: `advance_referral()` decides to
dispatch a phone call but has no row to point at, and `get_call_request()` needs one to
exist *before* the call is placed (it reads `provider_contact_phone`,
pickup/destination address + instructions from it). `get_or_create_booking_id`
materializes it the first time it's needed, sourced from what's already collected by
then: `service_requests` (pickup/destination) and
`service_application_channels.channel_contact` where `channel='phone'` (there is no
phone column on `services` itself). `/place-referral-call` now calls this instead of
requiring the row to pre-exist.

## 4. Ranking now caps the LLM shortlist and fails cleanly on zero-eligible

- **`SW_SHORTLIST_SIZE = 5`** — only the top 5 hard-filter survivors *by objective
  score* go on to subjective (LLM) scoring and get shown to the SW. Keeps the batched
  subjective-scoring prompt bounded regardless of how many services pass an
  over-permissive hard filter, instead of overloading it with everything that
  qualified. Final display order is still by *combined* score — subjective scoring can
  reorder within the 5.
- **`RankingUnavailable`** — zero hard-filter survivors is now a clean `422` with an
  explanation, not a bare `500`. Deliberately *not* caught by the existing
  degrade-to-unfiltered-fallback path: zero survivors usually means a real data problem
  (patient profile matches no active service, or the category's catalog is
  empty/misconfigured), and hiding that behind a normal-looking empty result is worse
  than surfacing it.
- **`eligible_count`** now rides along in both `POST /rank-referral` and
  `GET /ranking-results`'s response — total hard-filter survivors, not just the
  shortlist shown, so the SW screen can say "eligible for N services" even though only
  the top 5 are displayed.
- **`backend/main.py`'s `_rank_referral`** forwards a 4xx from the ranking service
  as-is (status + `detail`) instead of flattening everything into a generic `502` —
  a `RankingUnavailable` rejection is the ranking service's own clean decision, not an
  infra failure, and the SW should see the real reason. A genuine `5xx` (or an
  unparseable body) still becomes a `502`.
- **`frontend/src/api.js`** now surfaces a FastAPI `HTTPException`'s `{"detail": ...}`
  body in the thrown `Error`, instead of a generic `"422 Unprocessable Entity"` that
  told the SW nothing.
- **`frontend/src/ChooseService.jsx`** copy updated to state the eligible count
  directly ("eligible for N services, the most appropriate are below") rather than
  conflating it with the shortlist length.

## Test coverage

- `tests/test_worker.py` — 6 new cases for `voice_component`: empty queue, a
  successfully-placed call left `blocked` (not `completed`, and nothing re-dispatches),
  an unreachable call_agent marking the action `failed`, a missing
  `CALL_AGENT_BASE_URL` failing cleanly, the `escalated` path (closes + advances), and

  wired into the drain loop.

  its detail message verbatim; a genuine 5xx still becomes a 502 rather than being
  mistaken for a clean rejection.

Full suite passes with no regressions (157 tests as of this change).

## Verified live, 2026-07-31

Two separate real referrals were pushed all the way through consent → SW selection →
phone dispatch → a real Retell call → a confirmed booking, using the fixes above (the
`voice_component` poller was live-tested against the deployed `call_agent` on Railway
via an ngrok tunnel). Both hit the `save_call_outcome` bug described in §2 before the
fix landed — `service_bookings` stuck at `booking_status='pending'`, the
`contact_service_by_phone` action stuck `blocked` forever, no `notify_patient` action
ever queued. Both were manually repaired directly against the live DB (update the
booking row, close the action, call `advance_referral()`, queue `notify_patient`) to
confirm what the code fix above should now do automatically.
