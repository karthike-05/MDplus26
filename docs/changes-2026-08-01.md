## 2. Three bugs on the review-UI submit path

All three were on `POST /api/submit`, which had **never been run against the live DB**.

### 2a. `record_attempt()` was a guaranteed 500 on both live adapters

`ATTEMPT_COLS` maps `attempt_id` and `from_state` to `None` (no such columns exist
live). The body built its row by subscripting that map, so **both** landed on a single
literal `None` key, and `on_conflict=c["attempt_id"]` passed `None` to PostgREST as the
string `"null"`:

```
PGRST204  Could not find the 'null' column of 'attempts'
```

Fixed by making `record_attempt` **a documented no-op on both live adapters**, the same
call already made for `set_state` (§7a). It is not just safe, it is correct: live, the
same event is written by `record_shared_attempt` in *their* vocabulary, and a second row
would be counted by `advance_referral`'s per-channel exhaustion test — our `channel='form'`
isn't even in `attempts_channel_check`, and `attempt_number` is NOT NULL with no default.

### 2b. A successful submit made the referral abandon the service it had just applied to

`advance_referral` parks a referral at `waiting_for_response` only while some attempt has

```sql
status in ('queued','started','sent','delivered')
```

`STATUS_TO_THEIRS["success"]` was `("completed", "submitted")`, so a **successful**
submission read as an exhausted channel: the demo service (one channel) was instantly
marked `exhausted` and `advance_referral` returned `try_next_resource` one second after a
200 submit. Now `("sent", "submitted")` — pending, not concluded. `outcome` is untouched,
so the ranker still reads `submitted` and §7f's milestone distinction is preserved.

### 2c. The submit never closed the action, so the referral froze

The worker leaves `prepare_online_form` **blocked** awaiting a human, and this route *is*
that human — but it recorded the attempt and called `advance_referral` without closing
the action. The open-action guard then returned `{"state": "waiting", "reason": "An
action is already open"}` forever: the §7b failure shape, on the submit that just
succeeded. `_close_open_form_action()` now closes it first, best-effort and never fatal
(the injection already happened; failing the request would tell the SW their submit
failed when it didn't).

> Regressions for all three, plus §3: [`tests/test_live_submit_path.py`](../tests/test_live_submit_path.py).

## 3. Ranking's degrade path was itself the thing poisoning the key

`_run_unfiltered_fallback()` exists so a referral never parks on a poisoned
`rank:<referral_id>` dedup key when scoring fails (§7c). It wrote candidate rows with
`"score": None` — and **`referral_service_candidates.score` is NOT NULL**. So the
fallback raised, and the 500 it was written to prevent happened anyway.

`ranking_results.score` *is* nullable, which made the live symptom baffling: 59
`ranking_results` rows written, **zero** candidates, bare 500. Reproduced on `af536831`
after deleting its poisoned key — it re-poisoned immediately. Now `0.0`; ordering was
already carried by `rank`, and the `reasons` note is what marks them unscored.

> ⚠ **This fixes the code in this checkout only.** `service_ranking` is deployed
> separately on Railway. Confirmed via `eligible_count` in `GET /ranking-results` that
> the deployed instance *is* running the 2026-07-31 code — so this needs its own
> redeploy before `af536831` can recover. **And that redeploy alone is not enough** —
> see §8: a second, independent bug sat underneath this one.

## 4. Why every objective score was 77.5

Reported as "all 78 except the #1 Synthetic". The breakdown was identical for every real
service:

```json
{"cost": 100.0, "distance": 70.0, "hours_match": 70.0, "responsiveness": 70.0}
0.35(70) + 0.25(100) + 0.20(70) + 0.20(70) = 77.5
```

`70.0` is `NEUTRAL_SCORE` — "couldn't compute". **Three of the four components were
constant**, not one:

| Component | Why it was neutral | Status |
| --- | --- | --- |
| `distance` (0.35) | 0 of 46 `locations` had lat/long | ✅ fixed — 27 geocoded |
| `responsiveness` (0.20) | `response_time_hours` NULL on 57 of 58 services | ❌ catalog data, uncollected |
| `hours_match` (0.20) | no operating-hours data at all | ❌ catalog data, uncollected |

New: [`backend/scripts/geocode_locations.py`](../backend/scripts/geocode_locations.py)
— dry-run by default, reuses the same US Census geocoder already trusted for patient
addresses (`backend/intake/geocode.py`), so services and patients are placed by one
source. 27 of 30 addressable locations resolved; the 3 misses are all the same VA
address the Census geocoder can't parse. 16 locations have no `addresses` row at all.

Distance now discriminates: **7 distinct scores instead of 1**, Kansas City services at
99.8/99.7/95.2 and the Los Angeles ones at 0.0. Verified by computing `_distance_score`
directly against live data — no Claude call.

Adding coordinates alone only unsticks 35% of the weight. Until `response_time_hours` and
hours are populated the scores will still cluster more than they should.

## 7. Hardening for a link handed to judges

Audited the app as an untrusted visitor would use it, not as a scripted demo.

- 🔴 **`ALLOW_LIVE_CALLS`, default off.** 23 live services carry a real phone number and
  11 have `phone` at priority 1 — anyone picking one made Retell dial a real
  organisation. Off, the action is not claimed and stays `ready` (not `failed`, which
  would poison its dedup key and make the queue undrainable later).
- 🔴 **`VITE_DEV_TOOLS`, default off**, now hides the **Integration tab** and the
  **Mock/Supabase toggle**. That toggle swaps the adapter process-wide — one click
  changed the data source for every concurrent visitor.
- **Confirm before a real WhatsApp.** "+ New referral" names the number in the dialog;
  a generic "are you sure?" wouldn't catch a mistyped digit.
- **Escalations screen (B2 — closed).** `advance_referral` queues
  `escalate_to_social_worker` on four paths and nothing polls that component *by
  design*, because a person is meant to be the poller — but there was no screen, so a
  declined referral dropped off the board into a queue nobody could open. A referral
  tool that silently loses its failures is the exact thing this product replaces.
  `GET /api/escalations` + `POST /api/escalations/{id}/resolve`; resolving closes the
  action (else the open-action guard freezes the referral after a human has handled it).

All three flags are documented in [CLAUDE.md §2a](../CLAUDE.md#2a--the-three-flags-that-stand-between-this-app-and-the-real-world),
linked from the table of contents.

## 8. The ranking 500, actually root-caused

Blamed on NULL lat/long, then on `max_tokens=2048` truncating a 58-candidate prompt.
**It is neither.** Reproduced against the live DB for `af536831`: the hard filter passes
55/59, objective scoring succeeds for all 55, the top 5 shortlist is fine. The throw is
inside `run_subjective_scoring`, and with `stop_reason='tool_use'` — nothing truncated:

```python
tool_use.input == {"scores": "[{\"service_id\": ...}]"}   # a 1052-char STRING
```

`for row in <str>` iterates characters, so the first `row` is `"{"` and
`row["service_id"]` raises `TypeError: string indices must be integers`. Three
consecutive identical calls returned **three different shapes** — a proper list, that
JSON string, and a bare dict — so this is flaky structured output, not one deterministic
upstream bug. (The prompt likely contributes: `need_description` is NULL on patients
created through our intake, so the model scores fit against "Not specified.")

That `TypeError` propagated to the unfiltered fallback, which had its own NOT NULL crash
(§3) — **two independent bugs stacked into one opaque 500.** `_parse_subjective_scores`
now accepts every observed shape and skips malformed rows rather than throwing: losing
one candidate's subjective score beats losing the referral to a poisoned dedup key.

## 9. Messaging's notify handler failed on every attempt

Open item #2 from the 07-31 doc: `patient_comms`'s `_handle_notify` recorded a generic
`handler_error` on every `notify_patient` / `confirm_service_utilization` action, with
the real exception visible only in their logs. Found by reading rather than logs.

```python
repo.log_attempt(..., service_id=action.get("service_id"), conn=conn)   # no attempt_number
```

`log_attempt` defaults `attempt_number=1`, and `attempts` carries
**`UNIQUE (referral_id, service_id, attempt_number)`**. By the time we notify, that exact
triple is already taken by the outreach attempt that produced the booking — `c1a1e002`
has precisely that row from its Retell call. Duplicate key, every time.

It is also why **consent worked and notify never did**: `_handle_consent` passes
`service_id=None`, and Postgres treats NULLs as distinct in a unique index — `af536831`
has two `(NULL, 1)` rows coexisting happily.

**Fixed by passing `service_id=None`**, matching consent. Not merely to dodge the
constraint: a patient notification is a message to the *patient*, not an attempt on the
*service*. Recorded against the service it would be counted by `advance_referral`'s
per-service three-attempt cap and silently burn an outreach attempt on a text the
service never saw. Computing the next attempt number instead would NOT work —
`log_attempt` clamps with `min(3, ...)`, so it collides again on the fourth.

Note the send happens before the failing insert and `session.rollback()` cannot recall a
WhatsApp: the patient **was** receiving the message while the DB recorded failure and the
referral deadlocked on an open action. Same shape as the `save_call_outcome` bug (07-31
§2) — don't let bookkeeping roll back a side effect that already left the building.

Regression added to their own suite (`backend/patient_comms/tests/test_poller.py`).
⚠ Not executed here — `sqlalchemy` isn't installed in this environment, so that suite
can't run locally (CLAUDE.md §11). Both files compile; Messaging should run it.

## 10. `ORG_BACKEND_URL` is not what this repo said it was

CLAUDE.md §7f and §13 both claimed it was the org-email seam and that setting it was
"one env var between the button and real org-email acceptance". **Wrong**, and the error
propagated into two handoff summaries before being caught. `patient_comms/org_events.py`
uses it for exactly one thing:

```python
_post_json(f"{base}/api/patient-comms/event", ...)
```

— the **patient-reply** seam (consent confirmed/declined, utilization verified). Org
email is a separate leg that is **not built on either side**: nothing produces it, and
there is no env var for it. Both CLAUDE.md sites corrected.

It is still unset. `integration_events` holds 4 rows, all `provider='karthik_form'` (our
own dashboard clicks) — Messaging has never posted to us.

## 11. Food is reachable; web forms are cut

**Food assistance added to intake.** `[Demo] Northside Community Food Pantry` existed but
was unreachable — `CATEGORY_OPTIONS` offered only `transportation`, so nothing could route
to a `food` service and the `food_assistance` schema could never be exercised through the
UI. Ranking returns exactly one candidate for it, which is fine (`MIN_ELIGIBLE_CANDIDATES`
is 1).

One backend change was needed: `create_referral` only wrote a `service_requests` row when
`category == "transportation"`, so a food referral got none and `home_address` rendered
blank. It now writes whenever intake collected anything. That row is the *only* place a
street address lives (`patients` has no such column, §7e), which is why both forms source
`home_address` from `service_request.pickup_address`.

**Web forms cut from scope (B1).** `WebInjector` has **never run** — `frontend/mock_form/`
is empty and no `*_web.json` exists, so there has never been a fixture. The repo claimed
otherwise in several places ("web and PDF are both first-class targets"; "works against
`frontend/mock_form/`"), and that was wrong, not merely optimistic. Corrected in CLAUDE.md
§2 (golden rule), §3, §4, §6, §9 and §13, and in `whats-left.md` B1.

The seam is fine — picking it up later means writing a fixture and running existing code,
not rearchitecting. Until then nothing should describe web form-filling as working.

## 12. `send_email` no longer claims a send it didn't make

`send_email` is a stub (B3) that returned `status="success"` with
`data={"sent": True, "stub": True}`. So a referral routed to an email channel advanced to
"awaiting service response" and the timeline read **email sent** — for a message never
composed. Nothing read the `stub` flag.

Reachable with nobody choosing it: `advance_referral` picks the email channel from
`service_application_channels` by priority and **12 live services carry one**. There is no
email control in the UI to remove — that's not where the dispatch comes from.

Now it reports **`needs_human`** when no provider is configured, so the referral lands in
the SW's Escalations queue, which is the truthful state: somebody has to email this
service by hand. Mirrors `make_phone_call`, which already stubs visibly rather than
pretending a call was placed.

Everything stays wired for later — the tool contract, `main.TOOLS`,
`OUTREACH_TOOLS["email"]`, and `backend_component._send_email`. Setting any of
`RESEND_API_KEY` / `SMTP_URL` / `EMAIL_PROVIDER_URL` flips it out of stub mode; only the
TODO body remains. Free tiers cover demo volume, so finishing it costs nothing but time.

The one UI line that asserted the phantom send now reads "not sent — no email provider
configured". The other email mentions are the service's contact address and the patient's
own email, which are fine.
