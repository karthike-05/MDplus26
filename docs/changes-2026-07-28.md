### How to deploy a change

Railway auto-deploys on push to `main`. **But `frontend/dist/` is committed**, because
Railpack provisions Python only and `npm` doesn't exist in the build image. So a UI change
needs:

```bash
npm run build && git add frontend/dist && git commit -m "rebuild frontend" && git push
```

Miss that and the deploy silently serves the previous bundle — which looks exactly like
your change not working. Compare the `index-*.js` filename at `/` against your local
`frontend/dist/`.

> **This tax is worth removing** if more than one person is touching the UI. Railway
> Settings → Build → Builder → **Nixpacks** should detect the root `package.json` (added
> in `43efe9d`) and provision Node. That combination has never actually been tried — the
> one Nixpacks attempt was on an older commit with no root manifest. If it works,
> un-ignore `frontend/dist/` and restore the build command
> `pip install -r requirements.txt && npm run build`.

## What we proved works

The **outbound consent leg, end to end, on live data**:

```
"+ New referral" in the UI
  -> POST /api/patients + /api/referrals        (rows in the shared DB)
  -> advance_referral()                          (consent gate)
  -> referral_actions: confirm_consent -> twilio
  -> Messaging's deployed poller claims it
  -> a REAL WhatsApp arrives on the patient's phone
  -> patient replies YES
  -> patients.consent_status = confirmed, referrals.consent_confirmed_at stamped
```

That's four services and a human, and it works. Everything below is about what happened
next.

## For Ranking (Pranav)

**`POST /rank-referral/{id}` returns a bare `500 Internal Server Error`** for referrals
created through our intake UI, while succeeding for the seeded demo patients. Two
referrals hit it (`57bdcf5d…`, `af536831…`); Jordan Ellis (`c1a1e002…`) ranks fine.

The response body is just `Internal Server Error` — no detail — so this came from
diffing the patients rather than reading your logs.

| Patient field | Jordan ✅ ranks | The two that 500 |
| --- | --- | --- |
| `latitude` / `longitude` | 39.1155 / -94.6268 | **NULL** |
| `postal_code` / `county` | 66102 / Wyandotte | **NULL** |
| `need_description` | full sentence | **NULL** |
| `mobility_needs` | `wheelchair_accessible_vehicle` | **NULL** |
| `household_size`, `income_status`, `insurance_type`, `is_veteran` | populated | **NULL** |

Strongest suspicion was distance scoring doing arithmetic on a `None` coordinate — **that
guess was wrong.** We since reproduced the actual cause directly against the live DB and
the live Claude API: see the "the `/rank-referral` 500 is not the coordinates" update in
[`handoff-ranking-candidates.md`](handoff-ranking-candidates.md) — it's
`run_subjective_scoring` truncating on `max_tokens=2048` when a sparse patient profile
lets too many candidates survive the hard filter, not the coordinates.

**We've fixed our half.** Intake now requires a street address and geocodes it into
`latitude` / `longitude` / `postal_code` / `county` before the patient row is written
([below](#3-intake-collected-an-address-and-threw-it-away)), so new referrals should
reach you with coordinates.

**What we'd still ask of you:** don't 500 on a sparse patient. A referral with no
coordinates should degrade — skip distance scoring, or return an unfiltered shortlist —
rather than throw. Two reasons this matters beyond tidiness:

1. **A 500 is terminal for that referral, not just that request.** Our worker marks the
   action `failed`, and `queue_referral_action` upserts on
   `(referral_id, deduplication_key)` **without resetting `action_status`**
   (CLAUDE.md §7c). So `rank:<referral_id>` is now permanently poisoned — `advance_referral`
   "queues" it, gets the dead row's id back, reports success, and no open action exists.
   The referral sits there looking healthy and does nothing, forever. Recovering needs a
   **DELETE** of the dead row; cancelling it is not enough.
2. Any patient created by a clinic user with a partial profile will look like this.
   Ours is the first, not the last.

### If you're building the SW ranking-review UI

You're taking on the screen where the social worker reviews the shortlist, sees the
agent's reasoning, and approves. Here's the ground you'd otherwise have to rediscover.

**The reasoning you want to display is already modelled** — `ranking_results` carries it
per candidate, and nothing renders it today:

| Column | What it's for |
| --- | --- |
| `subjective_score` / **`subjective_rationale`** | the LLM layer's score and its **prose reasoning** — this is the "why" to show |
| `objective_score` / `objective_breakdown` | the deterministic component and its per-factor jsonb breakdown |
| `combined_score`, `rank` | the ordering |
| `passed_hard_filter`, **`filter_reject_reason`** | why a service was excluded outright (e.g. `outside_service_area`) — worth showing, since "why is this org *missing*" is the SW's first question |

`referral_service_candidates.reasons` (jsonb) is the shortlist-level equivalent. **Note:**
on the live DB those rows currently carry `"_source": "demo_driver shim"` — our stand-in
from before you redeployed. Delete the shim rows and let your service write them.

**There is already a working selection gate — please extend it rather than replace it.**
`frontend/src/ChooseService.jsx` + `POST /api/referrals/{id}/choose-service`. It's
deliberately minimal (a list and a button); the reasoning display and approve/reject flow
you're describing is the natural next layer on it, and we'd rather you own that screen.

If you rewrite the endpoint, it must keep doing **all four** of these or the gate breaks
*silently* (`backend/main.py:988`):

1. `select_candidate()` — flag the chosen row. The SW gate **adopts** a candidate already
   flagged `selected`; without it `advance_referral` falls through to the old auto-picker,
   which only considers `available` rows — so the SW's own pick is the one row it skips.
2. `set_referral_service()` — point the referral at it.
3. **Close the open `select_resource` action.** Nothing polls `social_worker` — a human is
   the poller — so skipping this freezes the referral on the choice just made, because
   `advance_referral`'s first guard is "any open action → wait".
4. `advance_referral()` — hand control back. The gate's whole point is that the SW's
   choice, not a rank ordering, is what moves the referral.

It also forwards the label to your `POST /sw-feedback` (best-effort, non-fatal). If you'd
rather write `sw_feedback` directly from your own UI, tell us and we'll drop the forward —
we don't want it written twice. The live table's columns are
`referral_id, service_id, label, label_notes, need_embedding`; `need_embedding` is NULL
everywhere, which is B11 — the subjective layer can't learn from SW corrections until
something populates it.

**Why the SW chooses at all**, since it's load-bearing for your design: `sw_feedback` is
the *only* signal your subjective layer ever learns from. Auto-selecting doesn't just
remove a safeguard, it starves the feedback loop. That's why `003` exists.

### Also relevant to you

## What we fixed

### 1. `ORCHESTRATOR_TICK` never worked from `.env` — silently

The sharpest bug of the day, and it wasted a live debugging round.

```python
# worker.py, before — evaluated at IMPORT
ORCHESTRATOR_TICK = os.getenv("ORCHESTRATOR_TICK", "0") in ("1", "true", "yes")
```

`backend/main.py` imports `worker` at line 37 and calls `load_dotenv()` at line 47. So
the constant was always evaluated against an environment that had no `.env` in it yet.
Setting `ORCHESTRATOR_TICK=1` in `.env` did **nothing**, `/health` reported `false`, and
the sweep never ran. No error anywhere.

`backend_component.claim_ranking()` was already a function reading the env at call time —
which is exactly why `BACKEND_CLAIM_RANKING` worked from `.env` and this one didn't.

**Fixed:** `orchestrator_tick()`, `poll_seconds()` and `stale_after()` are now functions.

**Why the tests didn't catch it:** they did `monkeypatch.setattr(worker, "ORCHESTRATOR_TICK", True)`
— patching a module attribute tells you nothing about how the value is *sourced*. They now
drive the env var, plus a regression test asserting late binding.

> **Rule of thumb for this repo:** any `os.getenv` at module scope in something
> `backend.main` imports is a latent version of this bug.

### 2. Turning the flags on silently broke three unrelated tests

`ORCHESTRATOR_TICK` and `BACKEND_CLAIM_RANKING` in `.env` changed what the suite
asserted, because `backend.main` calls `load_dotenv()` at import. `tests/conftest.py` now
blanks both at collection time, alongside the DB and seam URLs it already handled.

### 3. Intake collected an address and threw it away

`PATIENT_COLS` mapped `"address": None` — the live `patients` table has **no street
address column**, only `postal_code` / `county` / `latitude` / `longitude`. `_to_theirs`
drops keys mapped to `None`, so the address a social worker typed went nowhere, and the
four columns that *do* exist were never populated by anything. Hence the Ranking 500.

The address wasn't useless, it was **unmapped**: it's the input those four columns are
derived from.

**Fixed:** `address` is now **required** on `NewPatient`, and
[`backend/intake/geocode.py`](../backend/intake/geocode.py) resolves it via the **US
Census geocoder** (free, keyless, and authoritative for county — a ZIP-to-county table
would only approximate it).

Two traps, both wrong-but-believable, pinned by tests:

- the payload's **`x` is longitude and `y` is latitude**, the opposite of reading order;
- it carries a `County Subdivisions` entry reading `"Kansas City city"` right beside the
  real `Counties` entry `"Wyandotte County"`.

**Failure posture:** a timeout, a 500, an unparseable body, or no match all degrade to
`None` and the patient is still created — geocoding must never be why a social worker
can't do their job. But it does not fail *silently*: the response carries
`geocoded: false` and the UI warns that ranking will stall, because unresolved
coordinates mean the referral dies later inside a service we don't own.

### 4. `POST /api/patients` returned a 500 on a typo

Typing a letter into the date-of-birth field produced
`invalid input syntax for type date: "j"` — a raw Postgres error surfacing as a 500.
Now a **422** naming both accepted formats (`YYYY-MM-DD` and `MM/DD/YYYY`).

Phone is also normalised to **E.164** on the way in (`4088988088` → `+14088988088`).
That's the contract Messaging's provider docstring already assumes — *"the rest of the
app keeps storing plain E.164 numbers"* — and unnormalised, Twilio rejects it in **their**
logs, which reads on our side as a loop that silently stalled.

### 5. Live rows offered buttons that could only 409

`/run` and `/inbound` drive **our offline scheduler**. Live, `advance_referral()` owns
transitions, so `_require_our_scheduler()` answers 409 by design — but the UI still
rendered the buttons, so every click was a guaranteed failure dumping a raw error.

Live rows now name the owner of the step (*"the DB scheduler drives this live"*). The
**Review** button still works — that's ours either way — and a stray 409 explains itself.

### 6. `ALLOW_LIVE_INTAKE` — a guard before the app gets a permanent URL

This app has **no auth**. "+ New referral" kicks `advance_referral()` →
`confirm_consent` → `twilio` → Messaging's deployed poller → a **real WhatsApp to
whatever number was typed**, billed to the team's Twilio.

That was an acceptable risk for an ephemeral tunnel shared with three teammates for an
evening. It is not one for a permanent public deploy. New flag, **default off**: rows are
still created, only the outbound kick is withheld, and the response says so rather than
looking like a success. Surfaced at `/health`, because "no consent texts" otherwise looks
identical to Messaging's poller being down.

### 7. `demo_driver` called the SW gate "deadlocked"

It printed `⛔ NOBODY POLLS THIS — deadlocked` for `select_resource → social_worker`. A
human **is** the poller there, by design (CLAUDE.md §7b) — it's the demo, not a bug. It
was the single most likely thing to convince a teammate the whole system was broken. Now
reads `⏸ awaiting a human — the dashboard's "Choose service" screen completes it`.

### 8. `.gitignore` would have swallowed the next form schema

A bare `*.json` rule. Existing schemas are tracked so nothing was broken — git only
ignores *untracked* files — but the next `contracts/schemas/*.json` anyone added would
never have been committed, and the deployed review screen would 404 with the file sitting
happily on the author's disk. Negations added for `contracts/schemas/`,
`frontend/package.json` and `frontend/package-lock.json`.

### 9. The loop couldn't close on live data — fixed

`001_orchestration_bus.sql:81` promotes a referral only on an attempts row carrying
`enrolled`:

```sql
if exists(select 1 from attempts where referral_id=r.id and outcome='enrolled') then
  update referrals set status='enrolled' ...
```

**Nothing wrote it.** Our successful form submit records `outcome='submitted'` — which is
*correct*: submitting a form is not the org accepting, and collapsing those two would
destroy the exact distinction that is the product's differentiator (CLAUDE.md §7). The
gap was that nobody recorded the org's acceptance **at all**. So a live referral could
reach `submitted` and stop there permanently.

**`POST /api/org/response`** now closes it, living in the inbound adapter beside the Voice
and Messaging seams. It records the decision as a shared `attempts` row
(`direction=inbound`, `status=completed`, `outcome` from the live CHECK vocabulary) and
hands back to whichever scheduler owns transitions. Live rows awaiting a response show
**Org accepted ✓ / Org declined ✕** on the dashboard.

That button is a **manual trigger for a real seam**, not demo scaffolding — when Messaging
points `ORG_BACKEND_URL` at us, the parsed org email posts to the same endpoint and
nothing changes. A test asserts our own submit can never produce `enrolled`, because
collapsing milestone 1 into "we sent the form" is precisely what the incumbents do.

> **Checked live 2026-07-29: still zero.** Queried the live `attempts` table directly —
> 5 rows total, **none** with `outcome='enrolled'`. The mechanism works, but nobody has
> clicked *Org accepted ✓* on live data yet, and Messaging hasn't pointed `ORG_BACKEND_URL`
> at us either, so no real org email has posted to it. Walking Jordan's referral through
> a real *Org accepted* click is still the highest-value unproven thing (see the resume
> notes).

### 11. `service_requests` gets created now, and a silent write-back no-op is fixed

Two real bugs behind B13/B5 (blank transport-form fields), both fixed 2026-07-29:

1. **Nothing created the row.** `POST /api/referrals` now writes a `service_requests`
   row up front from whatever intake collected — the same street address already typed
   for geocoding (`pickup_address`), plus `appointment_date`/`appointment_time` when
   given. `home_address` in both PDF schemas now sources from
   `service_request.pickup_address` instead of the nonexistent `patient.address`.
2. **`save_service_request` was a bare `UPDATE`** on both live adapters — so on a
   referral with no row yet, a reviewer's first review-screen fill-in silently matched
   zero rows and vanished. The documented "self-heals after one manual pass" behavior
   (§6a) was **false on live data**. Both adapters (`supabase_api.py`, `supabase.py`) now
   upsert instead. Verified against the live schema in a rolled-back transaction (insert
   and update branches both proven, nothing committed).

Still open: `destination` (the service's own address) isn't collected or derivable
anywhere yet, and intake has no field for `appointment_time`. Both remain blank-but-
reviewable, same as before — narrower gaps than B13 originally described.

### 10. The worker reported work it hadn't done

`actions_serviced` read **580 after 145 idle ticks** — the Integration screen renders that
number, and it was false. The advance sweep returns one entry per open referral whether or
not anything happened, and `tick()` was folding those into the serviced count. Separate
counters now (`actions_serviced` / `referrals_advanced`).

The sweep also ran **every tick** — one `advance_referral()` RPC per open referral every
5 seconds against the shared DB, for no benefit. It has its own cadence now
(`ORCHESTRATOR_SWEEP_SECONDS`, default 30s) while the drain stays responsive at 5s.
